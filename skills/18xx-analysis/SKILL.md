## 1. 五阶段工作流

### S0 立规则（**不做这步，后面全错**）

1. **逐条读本作英文原规**，不要凭其他作品的记忆推断。
2. 列出**本作与已分析作品的机制差异**——至少覆盖这九项，逐项写进报告的 §0 或 §2：

| 维度 | 为什么致命 |
|:--|:--|
| 每轮铺轨次数 | 1830＝1 次；1846/1833NE＝2 次；18USA＝2 次且第二次付 $20；1853＝大 2/小 1；1880＝1 次且受建筑许可限制 |
| 领导头衔 | 1830/18USA/1833NE/1846＝president **总裁**；1853/1880＝director **董事（长）**。**按英文原词译，不跨作品统一** |
| 破产机制 | 1846「无破产」；1830 破产率 23.3%；1862 破产 61% |
| 随机属性 | 1862 的经营许可**每局随机绑定公司**——"某公司好/坏"必须拆到 (公司 × 许可) |
| 车辆与计分 | 1862 按许可限定车种、按时代强制报废；1846 是经典永久车 |
| 股票池 | `Bank Pool`（股票）与 `Open Market`（火车）是**两个不同的东西**；1880 干脆没有银行池 |
| 车站数量 | **印在公司面板上，不在规则书里**。1846：GT 3 / IC·NYC·B&O·ERIE·C&O 各 4 / **PRR 5** |
| 合并/收购 | 1862 合并的头号动机是**补证**（拿站 > 拿车）；1846 是资产腾挪 |
| 结束条件 | 1846 97% 打到 Phase IV 自然终局；1830 常见破产提前结束 |

3. 把**中文译本的可疑处**标出来——本项目一切以英文为准，中译有错要**指出并写明**（1880 官方中译的 Rust→"铁路"、2R→E 型车、持车义务语义反转；1817 中译是 OCR 稿错字多）。

### S1 数据入库：切分 · 查重 · 规范编号

```bash
cd D:/兵棋/18xx
python _tools/split_<作品>_cases.py "复盘分析/<作品>" -o "_work/<作品>_cases"
```

必须处理的三类源文件：**单局文件** / **带局头合订本** / **无局头合订本**（直接拼接，常以 ` -- Phase I (Operating Rounds…` 开头）。

- **按内容 sha1 去重**，不是按文件名或编号。历史教训：72 局稿实际只有 66 局；167 与 312 稿之间大量重叠。
- **输出规范编号 `作品-001.txt …` + `_mapping.csv`**（含源文件、行号、人数、胜者、内容指纹）。**此后一切引用以 `_mapping.csv` 为准，绝不用原始编号**——原始编号重号、错号是常态。
- 切分时顺带校验：**是不是本作品**（特征串，非本作自动跳过）、**有没有 `Game over`**（缺尾片段标出来）。
- **变体局单独标记**：1846 的 2 人局（起始 $600、持股上限 70%、Phase IV 仅 4 台车）、各作不同人数起始资金——**排除出主统计**，只在专门小节里说。

### S2 解析器：写一个能"对上账"的状态机

`_tools/parse_<作品>_log.py` —— 逐行重建：玩家现金/持股/市值/净资产 + 公司金库/火车/股价，按轮次输出快照，**末尾自动与日志官方结算对账**。

```bash
python _tools/parse_<作品>_log.py "复盘分析/<作品>/<作品>-001.txt"
```

**这是全流程唯一的质量闸门。** 对账口径：

```
玩家现金 = 起始资金 − 议会付款 − 买股(IPO/库存/股池) + 卖股 + 分红 + 补偿 + 期权股卖出 − 期权股赎回 − 义务罚款
持股     = Σ买入 − Σ卖出 − 退回 − 期权股卖出 ± 换股 ± 合并折算(2:1 缩股、残余非存续股 1:1 转存续股)
净资产   = 现金 + Σ(持股 × 终局股价)
```

**写解析器时逐条防这些日志句式陷阱**（1862 挖出 12 处，详见 `references/数据陷阱.md`）：所有格 `ESR's share price`、行尾 `(2 steps)`、含小写的公司名（`WStI`）、复数股数 `sells 9 shares of`、不写公司名的 `must sell 10% option share`、三方换股、合并末步残余股折算（**日志不逐笔记录**）、玩家名尾随空格、两种含义的 `removed`。

### S3 批量提取

```bash
python _tools/extract_<作品>.py     # → _work/<作品>_full.json
```

**纪律**：extract **复用 parse 的记账状态机、只旁听不改动**——这样对账仍然有效。跑完报出对账率：

- 1846 665 局：**2740/2740 = 100.0%**
- 1830 532 局：**532/532 = 100%**
- 1862 419 局：**1511/1572 = 96.1%**（残差中位 £203，已说明来源）
- 1880 China 341 局：**1564/1564 = 100.00%**（残差 0；剔除 17 局手动终止局后）

**对账不达标，不得进入 S4。**

### S4 专题统计

从 `_tools/*_1846.py`（14 个专题脚本）fork 改口径。**每问必跑，不能凭印象回答**：`combo`(首车组合) `rust`(爆车) `phase3`(爆车时点资金) `train`(公司间倒车) `stock`(买卖) `money`(金库/超发) `founding`(发起时点) `corp_profile`(公司画像) `misc`(顺位/par/车站/分红) `order`(顺位) `drop`(轮末砸价归因) `bomb`(爆破玩法) `earlyor`(开局四轮) `rating2`(前二制实力分)。

输出统一写 `_work/out<作品>/*.txt`，**报告里每个数字都要能指回某个脚本的某行输出**。

### S5 写报告

按 `references/报告模板.md` 的骨架写。写完自查 `references/交付前自查.md`。

## 2. 铁律（**不能犯错的地方**，共 18 条）

### 数据可信性（1–5）

1. **对账先行**。没有逐玩家净资产对账，任何结论都不成立。对账率要写进报告头部。
2. **内容去重**。不去重会虚增样本，还会把同一局的两个片段当成两局。
3. **不用原始编号**。重号/错号是常态，权威清单是 `_mapping.csv`。
4. **变体局隔离**。2 人局、不同人数、特殊变体不并入主统计。
5. **随机属性不跨局套用**。1862 的许可每局重绑；"这家公司强"是伪命题，必须写 (公司 × 许可)。

### 方法论（6–13）

6. **先分层再下结论**。用**独立于结论的估计**（Bradley-Terry / 前二制 rank rating）分层，**不能拿名次分组去解释名次**（循环论证）。残差口径要标注。
7. **口径**：前二制 rank rating = **第 1 名 +2、第 2 名 +1、第 3 名起 −(rank−2)**；建模时只构造「前二 vs 非前二」比较对，第 1 与第 2 之间不比、第 3 与第 4 之间不比。
8. **归一化名次 =(名次−1)/(人数−1)**，跨人数唯一可比。**场均名次不可跨人数直接比较**（3 人局理论均值 2.0、4 人局 2.5、5 人局 3.0）。
9. **前二率只在 ≥4 人局统计**（2 人局恒为全员、3 人局占 2/3，都没区分度）。
10. **样本量标注**：n<20 的格子只作参考；小样本高分玩家的置信区间宽达 300+ 分，**不能与厚样本玩家等同**；结论里要写清"样本翻倍后哪些弱信号变强、哪些强结论被确认"。
11. **相关 ≠ 因果**，每条因果嫌疑都要明写。典型：1846"GT 在底特律放站者结局更差"更可能是**被抢通道的被动反应**。
12. **统计"组合"而非"频次"**。问"这条线路上这家公司在什么时点用什么**车型组合**"，而不是"各类车买了多少次"——后者在游戏里没有意义（用户明确纠正过两次）。
13. **不编造**。每个结论都要**频次 + 频率 + 胜率 + 具体案例编号**四件套；没有数据就说没有。

### 规则准确性（14–17）

14. **一切以英文原规为准**，中文译本只用于对照用词，**发现误译要指出**（这可能就是用户最想要的部分）。
15. **具体数字必须查面板/规则**，不能凭印象（车站数量就是典型案例：规则书只写通用流程，数量印在公司面板上）。
16. **跨作品差异不得套用**（见 §1 的九项对照表）。
17. 引用规则**给条款号**（如 §5.34、§2.4.1、§6.5.4.3）。

### 匿名化（18）

18. **TOP 组保留真名，MID/BOT 组一律记作「玩家X」（英文版 `PlayerX`）**。这是**每一份 18xx 交付物**（主报告、英文版、速查、单局复盘、旧版、README、PPT）的强制要求——用户 2026-09-24 明确要求并已全量回溯应用。分层边界**各作品独立**（1846 按印出名单、1880 按 BT≥2.0、1830 按 BT≥1700/≤1420、1862 按 BT≥1700），编号按实力分降序、MID 段在前 BOT 段在后。工具 `_tools/anonymize_18xx.py`；**流程与五道校验见 `references/玩家匿名化.md`，做之前必读**。

## 3. 报告体例（**升级版，不是补丁页**）

### 固定骨架

```
# <作品> 深度分析（N 局）· vX.Y

> 文首块：分析人 / 使用模型 / 整理日期 / 版本沿革 / 数据基础 / 局型构成 / 对账率 / 规则依据

## 目录（表格式，篇 | 节 | 内容）
## 〇、数据与对账        ← 属性截面、对账明细、日志句式陷阱、局型构成
## 一、玩家层            ← 口径定义、实力榜、分层、熟人局/路人局
## 二…N、机制与行为各章   ← 每章先讲机制、再上数据、再给案例
## N+1、可执行结论速查    ← 编号清单，供上桌前背
## N+2、方法与局限        ← 工具、交叉验证、六条左右局限
## 附录                  ← 与其他作品的框架对接、脚本清单

*文末署名*
```

### 硬性写作要求

- **文首和文末都要署名**：`分析人：Pig9013 ｜ 使用模型：Deepseek-flash ｜ 整理日期：YYYY-MM-DD`。
- **文首和文末都要致谢 18xx.games 及站上玩家**（用户明确要求，见下方 §3.1）。**今后每一份 18xx 分析都必须带这条致谢。**
- **必须是自足的升级版**：用户**只会发布最新最全的一份**。新报告要把旧报告的**每一条结论、每一个机制解释、每一处样本警告**在新样本上重算后**全部保留**，数字变了标"（旧版 → 新版）"，方向变了的单独标注。**样本变大只能做得更好，不能更简单。**
- **不能只剩表格**。每张表后面要有解释性文字和案例，用户明确抱怨过"解释性话语和案例少了很多，不要图省事"。
- 每章开头**先讲清机制再谈策略**——读者是"规则已读、周末要上桌"的人。
- 文末要有**面向实操的速查**（可执行结论清单）。
- 旧版本报告**加横幅**指向新版本，不要留着让人误读。
- **玩家名一律按铁律 18 匿名化**：TOP 组真名、MID/BOT 组「玩家X」。**写完文档后、交付前**跑一遍
  `python _tools/anonymize_18xx.py --check` 确认无残留，PPT 走 `build_*_ppt.py` 重生成。详见 `references/玩家匿名化.md`。

| `_tools/ocr_pdf.py` | 直接用 | 扫描件中译 OCR（XY-Cut 双栏） |
| `build_<作品>_pdf.py` / `clip_<作品>_art.py` | 已迁出 | 规则书中译与原版式排版见 skill **`18xx-translation`**（样板脚本随迁） |

**从 0 开始一个作品的最短路径**：英文原规 → 差异表 → split → parse（对账到 100%）→ extract → rating2 → 专题脚本群 → 报告。**1846 是这套流程最完整的样板。**

**从 0 开始一部规则书中译的最短路径**：见 skill **`18xx-translation`**——英文原规 → 逐段对照中译 `.md`（术语裁决 + 勘误附表）→ 排版版 PDF（原版式 + 对应位置插图）。**Railways 与 1880 China 是两个样板（横版 1:1 / A4 竖版）。**

| 返工点 | 正确做法 |
|:--|:--|
| 报告越写越小 | 新报告必须 ⊇ 旧报告信息量 |
| 只剩表格没解读 | 每表配文字 + 案例 |
| 首车按车型频次统计 | 按**车型组合**统计 |
| 车站数量写错 | 查公司面板：GT 3 / 五家 4 / PRR 5（1846） |
| 分层用了名次 | 用 BT/RR 分分层 |

## 7. 输出经济（快照优先）

写文件是最大的输出开销（实测：模型 **96%** 的输出 token 花在工具入参上，聊天里说的话只占 4%）。三条能省，**但省 token 永远让位于留版本**：

- **改已有文件用 `Edit`，不整文件 `Write` 重写。** `_tools/*.py` 微调、报告补章节都走 Edit——实测 1846 报告被全量重写 **4 次**（浪费 69k 字符）、1862 报告 3 次（38.8k 字符）、`build_1846_ppt.py` 2 次（38.9k 字符）。
- **中间产物追加而非重生成**：`_work/` 下的逐局结果追加，别重写整份。
- **脚本能算的不要让模型手写**：`_full.json` 那类一律脚本生成，模型不碰。

### ⚠️ 快照纪律（优先级高于上面三条）

`Edit` 是**就地改**，改坏了没有整份可回退——而 AI 中途出错、需要回溯历史是常态，报告越写越小时尤其需要回看旧版。所以：

- **每 1–2 个对话窗口必须落一份完整版本快照**（整份可直接用，不是 diff）：报告类存 `报告_vX.Y_YYYYMMDD.md`，脚本类存 `_tools/_snapshot/YYYYMMDD/`。
- **改 `_work/` 数据或 `_tools/` 脚本之前先确认快照在**；没有就先复制一份再改。
- 这条**压倒**省 token：宁可多花那点输出钱，也不能出现"改坏了又回不去"。

## 9. 交付与发布（2026-10-25 起）

**每个 skill 一个独立仓库，不复用 `WITE2_CN`**。发布前按下表逐项过：

| 项 | 要求 |
|:--|:--|
| 发布物 | 主报告 `.md`、`.pptx`、英文版、术语表；**只发最新最全一版**，旧版留横幅 |
